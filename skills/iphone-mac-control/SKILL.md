# iPhone control from Mac

Resolve the repository root from this skill's location (`../..`). Read `docs/setup.md` for initial setup and command syntax. Do not reflash firmware or change network settings as a routine phone action.

## Fixed tools first

Use the installed MCP tools when they are actually present in the client's tool list. Otherwise use the repository's fixed executable `./iphone`: `observe`, `tap 12 --id p1 --wait 发布`, `tap --xy 378 296 --id s1`, `swipe 250 850 250 350 --id d1`, `type --id t1 --text-file runtime/draft.txt`, `image`. Resolve its absolute repository path if working elsewhere. Read [agent entrypoints](../../docs/agent-entrypoints.md) for registration, per-agent sessions and retries.

Do not generate ad hoc Python/urllib/heredoc HTTP scripts for routine observe/tap/input operations. The fixed CLI remembers the observed frame, builds requests, handles output and writes images. MCP/CLI return compact OCR by default; use full=true / global --full only when boxes are needed. A registered server is not proof the current session loaded its tools. If tools are not visible, use the fixed CLI now rather than repeatedly probing or inventing another transport.

Read each result before choosing the next action. Reuse an action's returned observation directly. CLI requests require a stable --id; after an ambiguous failure, retry with the SAME id and arguments. The CLI pins retries to the original payload even after a new observe. A new id means a new physical action, not a workaround for uncertainty.

### Await the complete result in one tool call

The CLI already waits synchronously for the API. When invoking it through `exec_command`, retain the default 10000 ms foreground wait or explicitly set `yield_time_ms: 10000`. Use 30000 for a known slower operation. Do not set 1000 ms, append `&`, or use nohup for ordinary phone actions. With `functions.exec`, retain its normal outer wait instead of adding a one-second yield pragma. Native MCP calls should likewise be awaited directly.

For example, invoke `exec_command` with `{"cmd":"iphone tap 12 --id task1-p1 --wait 发布","yield_time_ms":10000}`. A 2–3 second action returns its result in that same call; it does not wait the entire ten seconds. This command-tool foreground wait is separate from CLI `--timeout`, which controls how long the backend checks the phone's resulting state.

Only if the tool reports an actually running process after the foreground wait, poll that original session with a suitable wait (normally 10000 ms). Do not add a poll after a completed result and do not re-execute a phone mutation to fetch its output. For a still-running `functions.exec` cell, use its corresponding wait tool rather than starting another command.

## Observe and act

Prefer the persistent observation API/MCP described in [observation API](../../docs/observation-api.md). Call `iphone_observe()` for text and pixel centers; if MCP is unavailable, run `./iphone observe`. If the service is absent or unhealthy (`./iphone health`), use `./iphone serve status` and restart the affected service with `./iphone serve restart --api` or `./iphone serve restart --receiver`. Default to text observations; request `include_image=true` for ambiguous icons, stars, missing targets or unexpected results. MCP returns the matching image content block; CLI `--include-image` saves that same frame and returns its file path. Open the image only when visual judgment is needed. Do not pipe HTTP image base64 into the model as text.

Check `stale` before acting. Observation returns the latest readable frame immediately; it does not wait for a freshness threshold. If that frame is old or only a cached frame is available, the result includes OCR marked `stale=true`, its age and read mode. Use it to inspect the last known screen, but never use its coordinates for actions or text insertion. A temporary-unavailable result means there is no readable frame cache; it does not by itself prove the phone is locked or mirroring is disconnected. Do not tell the user to reconnect unless the screen itself or separate evidence confirms that. IDs and item numbers belong to one observation; obtain a new observation after page changes. OCR centers locate text, not guaranteed clickable controls: a Home Screen app label may require tapping its icon instead. OCR may misread characters; compare input against the known original and inspect again before editing suspected typos.

After any navigation or unexpected frame change, re-observe and re-derive coordinates before acting; if a page's title or header differs from the screen you measured, treat it as a different screen. Compound actions must be anchored — `taps` requires `--expect TEXT` and refuses to fire when the anchor is missing from the current frame; when it refuses, stop and inspect rather than retrying with adjusted coordinates. Fire one tap, read the returned observation, and decide the next — compound actions are for confirmed, stable layouts only. Treat any irreversible action (submit, publish, send, pay, delete) as requiring explicit verification of the form content BEFORE the final tap, because many such actions cannot be undone.

Observations also include `airtype`: when the current keyboard panel is readable, it contains endpoint/host/port and a six-digit `pairing_code` string. This is extracted from the same OCR, not another screenshot. It is not a verified connection or a saved Token. Missing/ambiguous/stale codes are null; never substitute a historical code. Prefer `iphone_type` to orchestrate connection and insertion rather than manually assembling calls.

Color states (selected/unselected, on/off, rating levels) are invisible to OCR text; use `./iphone pixel --xy X Y` (or several X Y pairs in one call — one frame fetch serves all points) to sample colors, and `--compare R G B [R G B ...]` to get a boolean `filled`/`distance` judgment. The selected/active color is APP- AND THEME-SPECIFIC (different apps use different accent colors); do not assume any fixed value — sample a control in its known-selected state first, or pass multiple references and let `filled` match any. Caveat: after a tap the ESP32 pointer cursor stays on that spot and darkens samples taken there; the CLI warns with `near_last_tap` when this is likely. When a sample looks dim or ambiguous, cross-check a NEIGHBORING element of the same kind — never click somewhere "harmless" to move the cursor: in forms and editors any coordinates may be an active control, and a stray click can submit, navigate, or modify content. Prefer resolving ambiguity through the page's own text (apps often label the selected state, e.g. a caption next to the control).

App flows commonly interpose confirmation dialogs and success screens whose wording varies per app. Read the dialog before tapping; dialogs appear after actions and their buttons are decisions (submit vs keep editing). Never wait on a hardcoded success phrase — observe the actual post-action screen once, note its real wording, then wait on that; `wait` accepts `|`-separated alternatives when wording is uncertain. `type` auto-rechecks once when immediate verification is `not_confirmed`, matching the inserted prefix or suffix across all OCR lines (render lag of ~1s is normal; status becomes `confirmed_on_recheck`) — do not manually re-observe before that recheck completes. Forms may auto-scroll when a control gains focus or a value is set, so controls move — re-locate them by OCR before sampling or tapping again. After tapping a stateful control, prefer `tap --wait <state-label>` (apps label the selected state next to the control) over sampling pixels at remembered coordinates. Live feeds (camera previews, video pages) never reach a stable frame, and some pages swallow taps while reporting them accepted: `tap --retry N` handles both automatically — it retries refused taps and re-fires accepted-but-ineffective taps only when the frame still matches the pre-tap layout and the `--wait` text never appeared. Collapse keyboards with `./iphone dismiss` — it tries every known strategy (chevron, panel close, scroll-blur) and verifies the keyboard is gone; pass `--reveal TEXT` when the real goal is just to uncover a control, and it succeeds as soon as that text is visible. Before tapping an action button in an order list, confirm which order it belongs to — adjacent orders show lookalike buttons (评价返现 appears on ALREADY-reviewed orders too); scroll the occluding banner away with `./iphone scroll --until` and tap the button for the intended order, then verify the editor's product line matches before going further.

Infrastructure diagnosis lives entirely in the CLI: `./iphone health` (observe API actions/input availability), `./iphone board status` (raw board firmware/USB/network state), `./iphone receiver` (frame sequence plus API health), `./iphone board discover --save` (find the HID bridge on the LAN — its DHCP address can change after power cycling; do not assume a remembered IP), and `./iphone serve restart` to restart the stack. If observations work but every tap has no effect, check `./iphone health` — `actions_enabled:false` means the API was started without the board. Floating banners and promo strips often occlude controls; `./iphone scroll --id s1 --until '控件文本'` swipes repeatedly until the control's text appears (or `--gone`), with `--max`/`--dir` bounds and a timeout that keeps the final observation.

The keyboard's tiny footer may require the built-in local OCR crop; valid IP and .local URLs can coexist. Do not guess punctuation/digits in an unreadable address or lower code confidence to force input. If discovery fails, inspect the current image and use the documented manual client fallback. For wait_for_text, use text actually displayed in the phone's language: this AirType setup shows 配对码 / 网页输入, not necessarily “Web”.

Diagnose the pipeline with the CLI instead of ad-hoc probes: `./iphone receiver` shows whether the UxPlay receiver is receiving frames, `./iphone board status` shows the board's firmware/USB/network state, and `./iphone serve restart` restarts the receiver and observe API when either is down (see `./iphone board discover --save` if the board IP is unknown). The `runtime/latest.jpg` file is a fallback for image viewing only when OCR is unavailable. The phone must mirror to **iPhone Agent Mac**, not the board. Never hardcode another user's board address.

Coordinates are actual screenshot pixels, not 0–1000 prompt units; `./iphone tap` and `./iphone swipe` (see `--xy`) send absolute HID positions through the board.

Prefer `iphone_act` for configured deployments; read [action API](../../docs/action-api.md) for setup and argument details. It combines tap/swipe, a bounded stable-screen wait and new OCR in one call. Supply the current observation_id and a unique request_id; tap by target_id OR pixel x/y, swipe by x/y/end_x/end_y. Text targets are revalidated by text and position; unanchored pixel clicks require the OCR layout to remain consistent. Choose specific expected page text via wait_for_text when useful. It serializes actions with AirType. CLI commands above remain a fallback, not an additional step after a successful API action.

Use its returned observation and IDs directly for the next decision. If the current frame is stale, the action endpoint makes one non-click pointer move in an OCR-empty area and requires a newly received changed Mac frame; it then revalidates the target text or layout. If the probe cannot confirm a new frame or no OCR-empty probe location is available, no tap/swipe is sent. The pointer move itself may be visible on screen. The tap/swipe is never retried automatically; after an action, the endpoint waits for newly received frames. Do not call iphone_observe again merely because an action happened; request another observation only if the result is missing, stale, incomplete for the next target or otherwise uncertain.

Read `wait.status` separately from `accepted`: condition_met means expected text on a changed stable screen; changed means only stable OCR content change; timeout/no_new_frame/observation_unavailable do not confirm completion. A newly received frame alone is not success. Reuse the SAME request_id and action parameters after timeout; a durable claim prevents re-execution, even after restart. Never issue a new ID to blindly repeat publishing. The result includes observation, added/removed items and timings; changes_only=true omits full items, include_image=true attaches the result frame. Removed IDs belong to the old frame; obtain full current OCR before targeting an unchanged item omitted from a delta. Layout checks cannot detect every non-text overlay or frozen replay.

Observe after each navigation before using coordinates on the new page. Batch only actions whose targets and effects are already known; do not blind-tap through dialogs or across unseen pages. Transport `ok` is not evidence of success. Verify submission using visible success text or the resulting record, and avoid duplicate submissions after ambiguous results.

The receiver's sequence and arrival time show frame reception, not semantic freshness or measured capture latency. If actions show no effect, compare frames and check USB/status/source.log. Replan after repeated misses; stop after two failed stream recovery attempts and report the actual state. Do not repeatedly restart mirroring without progress.

## Home and input

Consumer Home did not work on the test phone. Return Home with a bottom-edge upward swipe scaled to the actual screenshot. `command 'key cmd+space'` can open Spotlight; verify before typing.

Prefer **AirType LAN insertion** for Chinese or other non-ASCII text when installed. Read [Chinese input](../../docs/chinese-input.md) for setup, commands and recovery. Focus the intended field and show AirType's Web Access keyboard, then call `iphone_type(text=..., request_id=...)`. It reads the fresh OCR address/code, reuses or pairs the session, inserts once, checks OCR, and returns that post-input observation in the same result. Set `include_image=true` to also receive the matching frame. Use a unique request_id for each intended insertion; reuse the SAME id and text on timeout/retry. Never switch IDs to bypass an uncertain result: inspect the field first. The durable local journal prevents replay of an attempted command even after service restart. `accepted:true` is not proof of correct focus; `verification.status:text_detected_after_input` is only OCR evidence, and `not_confirmed` does not mean insertion failed.

If MCP is unavailable, use `./iphone type --id t1 --text-file runtime/draft.txt`; HTTP is a backend implementation detail, not a reason to generate a request script. If automatic discovery is ambiguous or unavailable, inspect the current panel and fall back to `tools/airtype.py pair --code CURRENT_CODE` and `type --text-file runtime/draft.txt` (both with `--host PHONE_IP`). No cloud or clipboard transfer is needed. Never use a historical pairing code; reopening the keyboard may change it. Saved sessions live only in ignored runtime files. Input is separate from submission; the wrapper never clicks Send/Publish.

After insertion, compare the visible text with the intended original before publishing. On timeout, inspect before resending to avoid duplicates. Do not type test phrases into a real answer or message draft and submit them. Request newline permission in the CLI only for an observed multiline editor.

Fallback when AirType is unavailable: `command 'type ...'` sends ASCII key events. Select **简体拼音 / 全键盘**, send short pinyin phrases, inspect and select the correct candidates. A nine-key layout can produce wrong input. Trailing spaces in `type` are trimmed; send `command 'key space'` separately or tap the candidate. `cmd+a` may not select all during active pinyin composition: commit or clear composition first. Do not silently substitute English for requested Chinese.

Do the task the user authorized. For product questions, ask for missing first-hand facts when needed; do not infer authenticity or specialized efficacy from a general positive purchase experience. Read `docs/validation.md` when compatibility or performance matters.

### Prefer complete action results

For navigation and submission, supply `--wait` / `wait_for_text` with visible destination text when known (alternatives use `|`). Reuse the returned OCR and timestamped image path for the next action. `wait.stable` confirms a settled changed layout; `wait.target_confirmed` confirms the requested text persisted. Neither `accepted` nor `changed` proves publication. Additional observe calls are for missing/incomplete/loading/timeout results, not an automatic step after every action. See `docs/action-api.md` for the settling policy.
